# Backend API Contracts

## Design Principles

The API should be:

- stable for the frontend
- explicit about scenario type
- structured enough to validate safely
- decoupled from internal graphql-gene implementation details

The frontend should never need to know how the backend builds or executes the runtime.

## Base Concepts

Every request should include:

- a `scenario` identifier
- a structured `input` object
- an optional `view` or panel preference

Every response should include:

- a `requestId`
- a `status`
- structured result data
- diagnostics

## Endpoint 1: Load Examples

### `GET /api/playground/examples`

Returns the curated example catalog used by the UI.

Example response shape:

```json
{
  "requestId": "req_123",
  "status": "ok",
  "examples": [
    {
      "id": "polymorphic-blocks-basic",
      "scenario": "polymorphic-blocks",
      "title": "Polymorphic Page Blocks",
      "description": "Query heterogeneous CMS blocks with inline fragments.",
      "editableFields": ["query", "path", "blockSelection"]
    }
  ]
}
```

## Endpoint 2: Generate Schema

### `POST /api/playground/generate`

Purpose:

- generate SDL
- return type summaries
- return diagnostics

Example request shape:

```json
{
  "scenario": "model-to-schema",
  "input": {
    "exampleId": "user-orders-basic",
    "modelEdits": {
      "includeOrders": true,
      "includeAddress": true
    },
    "options": {
      "showTypeSummary": true
    }
  }
}
```

Example response shape:

```json
{
  "requestId": "req_124",
  "status": "ok",
  "scenario": "model-to-schema",
  "schema": {
    "sdl": "type Query { ... }",
    "typeSummary": [
      {
        "name": "User",
        "kind": "object",
        "fields": ["id", "username", "orders"]
      }
    ]
  },
  "diagnostics": []
}
```

## Endpoint 3: Execute Query

### `POST /api/playground/query`

Purpose:

- execute a curated demo query against a seeded scenario
- return result data
- return include graph or execution metadata

Example request shape:

```json
{
  "scenario": "query-lookahead",
  "input": {
    "exampleId": "me-with-orders",
    "query": "query MeForAccount { me { id email orders { id status } } }",
    "variables": {}
  }
}
```

Example response shape:

```json
{
  "requestId": "req_125",
  "status": "ok",
  "scenario": "query-lookahead",
  "result": {
    "data": {
      "me": {
        "id": "1",
        "email": "user@example.com",
        "orders": [
          { "id": "10", "status": "PAID" }
        ]
      }
    }
  },
  "execution": {
    "includeGraph": {
      "User": ["orders"]
    },
    "notes": [
      "orders was loaded because it was requested in the selection set"
    ]
  },
  "diagnostics": []
}
```

> **Amendment (2026-05-20):** Add a `sql` field inside `execution` for scenarios that use Sequelize. The field contains the SQL string generated by Sequelize for the query, formatted as a single readable string. It is `null` for scenarios that do not involve a database query.
>
> Updated `execution` shape:
>
> ```json
> "execution": {
>   "includeGraph": {
>     "User": ["orders"]
>   },
>   "sql": "SELECT \"User\".\"id\", \"User\".\"email\", \"orders\".\"id\" AS \"orders.id\", \"orders\".\"status\" AS \"orders.status\" FROM \"Users\" AS \"User\" LEFT OUTER JOIN \"Orders\" AS \"orders\" ON \"User\".\"id\" = \"orders\".\"userId\";",
>   "notes": [
>     "orders was loaded because it was requested in the selection set"
>   ]
> }
```
```

## Endpoint 4: Inspect Directive Scenario

### `POST /api/playground/directives`

Purpose:

- render a directive-focused demo
- show runtime behavior and schema-printing impact

Example request shape:

```json
{
  "scenario": "directive-middleware",
  "input": {
    "exampleId": "user-auth-directive",
    "directiveMode": "named"
  }
}
```

Example response shape:

```json
{
  "requestId": "req_126",
  "status": "ok",
  "scenario": "directive-middleware",
  "directive": {
    "name": "userAuth",
    "printsToSchema": true,
    "runtimeBehaviorSummary": "Loads authenticated user context before field resolution."
  },
  "schema": {
    "sdlExcerpt": "type Query { me: AuthenticatedUser @userAuth }"
  },
  "diagnostics": []
}
```

## Shared Error Shape

All non-successful responses should follow one safe structure:

```json
{
  "requestId": "req_127",
  "status": "error",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The selected example payload is not valid.",
    "details": [
      "query must be a string"
    ]
  }
}
```

## Validation Rules

The backend should validate:

- allowed `scenario` values
- allowed `exampleId` values
- maximum query length
- maximum variables size
- allowed editable fields per scenario

## Versioning

For MVP, unversioned endpoints are acceptable if the frontend and backend ship together. As soon as the API becomes independently consumed, introduce versioning such as `/api/v1/playground/...`.
